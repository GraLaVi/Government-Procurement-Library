# Sitemap and robots.txt

What search engines are told about the public site: the URL list at
**`/sitemap.xml`** and the crawl rules at **`/robots.txt`**. This document is
the maintainer's guide — what is published, why each exclusion is deliberate,
and what you have to do (usually nothing) when a page is added.

## What it is

- **`https://www.gphusa.com/sitemap.xml`** — 32 URLs in one flat sitemap:
  the marketing pages, the five product pages, the Help Center and all 17 of
  its articles, and the three legal pages. Each entry carries `<lastmod>`,
  `<changefreq>`, and `<priority>`.
- **`https://www.gphusa.com/robots.txt`** — `Allow: /`, a `Disallow` list
  covering the signed-in application, and the `Sitemap:` directive pointing at
  the above.
- Both are Next.js metadata routes, **prerendered as static content at build
  time** (`○ /sitemap.xml`, `○ /robots.txt` in the build manifest). They cost
  nothing per request and are regenerated by every `npm run build` — which is
  what makes new help articles appear without a separate publish step.

## File map

| Path | Role |
|---|---|
| `src/lib/sitemap.ts` | **Single source of truth** — canonical origin, which paths are public, fallback `lastmod` dates, per-section `changefreq`/`priority`, and the robots `Disallow` list. |
| `src/app/sitemap.ts` | Serves `/sitemap.xml`. Resolves each entry's `<lastmod>` (frontmatter first, registry second) and emits the XML. |
| `src/app/robots.ts` | Serves `/robots.txt` from `DISALLOWED_PREFIXES` + `SITE_URL`. |

The URL list is **derived, not duplicated**: help articles come from
`HELP_ARTICLES` (`src/lib/help.ts`) and product pages from `PRODUCT_PAGES`
(`src/lib/products.ts`), the same registries that drive those routes'
allowlists. A page cannot be in the sitemap unless it is in the registry that
makes it exist, and it cannot be missing from the sitemap once it is — the two
can't drift. Only the handful of one-off marketing pages are listed literally.

Product entries respect `href: null` in `PRODUCT_PAGES`, which marks a product
whose page is not written yet (a greyed-out nav card). Those are skipped: never
hand a crawler a URL that 404s.

## The `www` host is not cosmetic

`SITE_URL` is `https://www.gphusa.com`, hard-coded. The apex (`gphusa.com`)
301s to `www` at Cloudflare's edge and the origin's Let's Encrypt cert only
covers `www` — see the comment above the `server` blocks in
`nginx/nginx.production.conf`. So `www` is the only spelling that answers
directly, and it is the one form a crawler should ever be given: a sitemap full
of redirecting URLs spends crawl budget on hops and muddies which host owns the
ranking. `gphusa.com/sitemap.xml` still resolves — via that same redirect.

It is a constant rather than an environment variable on purpose. Dev and prod
run the same code path (no divergent behaviour to reason about), and a sitemap
is only ever fetched from production.

## `<lastmod>`: where the dates come from

Two sources, in this order:

1. **`last_updated` in the page's own markdown frontmatter**, for `/help/*` and
   `/legal/*`. This is the date the article already displays, so the byline and
   the sitemap cannot disagree, and one edit updates both. Today only
   `privacy.md` and `terms.md` carry one.
2. **The fallback tables in `src/lib/sitemap.ts`** (`MARKETING_ROUTES`,
   `PRODUCT_LASTMOD`, `HELP_LASTMOD`, `LEGAL_ROUTES`), seeded from `git log -1`
   per file when the sitemap was built (Sept 2026).

If neither exists, the entry ships **with no `<lastmod>` at all**. That is
deliberate. The field is optional, and the tempting alternatives — the build
timestamp, or `fs.stat` mtime — both mark the entire site as changed on every
deploy or every fresh clone. Google discounts `lastmod` it finds untrustworthy,
which would cost us the recrawl signal that is the entire reason to publish
dates. An omitted date is honest; a moving one is worse than nothing.

**Why the tables are maintained by hand:** `.dockerignore` excludes `.git`, and
`npm run build` runs *inside* the Docker build (`RUN npm run build` after
`COPY . .`), so nothing can shell out to git at build time to recompute them.

Bump a date when the *copy* changes. Leave it alone for a refactor that renders
the same page.

The `/help` and `/products` index entries need no maintenance: both are
generated from their registries, so each genuinely changes the day a child is
added, and each takes the newest date among its children automatically.

`<changefreq>` and `<priority>` are applied per section by `publicRoutes()`.
Google ignores both; Bing and smaller crawlers still read them and they cost
nothing to emit.

## What is excluded, and why

Everything below is still **crawlable** — it is simply not advertised as a
ranking target. Absence from a sitemap is not a `noindex`.

| Excluded | Why |
|---|---|
| `/login`, `/forgot-password`, `/reset-password`, `/verify-email` | Auth flows with nothing to rank. |
| `/signup` | Renders differently per `?tier=` / campaign query string, which would seed the index with thin duplicate variants of one page. |
| `/contact/success` | Post-submit thank-you page. |
| `/start/*` | Paid-traffic campaign landings (`src/lib/campaigns.ts`). They exist to be linked from an ad or an email, and would otherwise compete with `/pricing` for the same organic query. |

If a campaign page ever needs to be kept out of results outright — not merely
unadvertised — that takes a `robots: { index: false }` metadata export on the
route itself. `robots.txt` governs crawling, not indexing: a disallowed URL can
still be indexed from inbound links and show up with no snippet.

`DISALLOWED_PREFIXES` covers the signed-in application (`/account`,
`/dashboard`, `/analytics`, `/bidmatching`, `/library`, `/rfq`), `/api/`, and
the URLs carrying a single-use token (`/reset-password`, `/verify-email`) —
fetching those is not a read-only act. Every app route renders an access-denied
shell to a logged-out visitor, so crawling them would spend budget to index
nothing. The prefixes have **no trailing slash** because `/account`, `/rfq` and
`/dashboard` are pages in their own right and a bare prefix covers the page and
everything under it. `Disallow` is a prefix match on the path, so `/analytics`
does not touch the marketing page at `/products/analytics`.

## How to add a page

- **A help article** — nothing to do. Drop `<slug>.md` in `src/content/help/`
  and add its `HELP_ARTICLES` entry as usual (see `docs/help-center.md`); the
  next build publishes it. It ships without a `<lastmod>` until you give it one
  — either `last_updated` in its frontmatter or an entry in `HELP_LASTMOD`.
- **A product page** — nothing to do beyond setting its `href` in
  `PRODUCT_PAGES`. Add a `PRODUCT_LASTMOD` entry for a date.
- **A new marketing page** — one line in `MARKETING_ROUTES`. Consider whether
  it also belongs in `AUTH_CONFIG.ROUTES.PUBLIC`, or `proxy.ts` will bounce
  signed-out visitors (and crawlers) to `/login`.

## Gotchas

- **`proxy.ts` lets these through on a technicality.** The auth middleware
  allows any request whose `pathname.includes('.')` before it checks tokens,
  which is what exempts `/sitemap.xml` and `/robots.txt` — neither is in
  `AUTH_CONFIG.ROUTES.PUBLIC`. If that escape hatch is ever tightened, add both
  paths to the allowlist explicitly, or signed-out crawlers start getting a
  302 to `/login` and the sitemap silently stops working.
- **Verify after deploy, not just locally.** `curl -sI https://www.gphusa.com/sitemap.xml`
  should return `200` with `content-type: application/xml`.
- **Search Console submission is manual and one-time.** Search Console → the
  `www.gphusa.com` property → **Sitemaps** → submit `sitemap.xml`. Google
  recrawls it on its own afterwards; re-submitting is only needed if the URL
  itself changes.
- **`gzip_types` in `nginx.production.conf` lists `text/xml`, not
  `application/xml`**, which is what Next serves the sitemap as — so the
  response is currently uncompressed. It is a few KB, so this is a nicety, not
  a bug.
- **One flat sitemap, not a sitemap index.** The protocol's limits are 50,000
  URLs and 50 MB uncompressed; we publish 32. Split it only if the public
  surface ever grows by three orders of magnitude.
